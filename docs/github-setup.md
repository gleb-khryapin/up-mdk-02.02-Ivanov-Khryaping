## 2. Защита ветки main (Branch Protection Rules)

Settings -> Rules -> Rulesets -> New ruleset -> New branch ruleset.

| Параметр | Значение |
|---|---|
| Ruleset Name | `main protection` |
| Enforcement status | Active |
| Target branches | Add target -> Include default branch |

Включить правила:

- **Restrict deletions** - запрет удаления ветки;
- **Require a pull request before merging** - прямой пуш в `main` запрещён;
  - Required approvals: `1` (обязательный Code Review);
  - Dismiss stale pull request approvals when new commits are pushed;
- **Require status checks to pass** - обязательное прохождение CI;
  - добавить проверки `Серверная часть` и `Интерфейс`;
  - Require branches to be up to date before merging;
- **Block force pushes** - запрет перезаписи истории.

Важно: проверки появляются в списке только после первого запуска CI,
поэтому сначала отправьте любую ветку и дождитесь выполнения конвейера.

## 3. Канбан-доска

Вкладка Projects -> New project -> шаблон Board -> название «Учебная практика УП.02».

Колонки по обновлённому заданию (создаются кнопкой «+» справа от заголовков):

```
Backlog -> Ready -> In Progress -> Code Review -> QA -> Done
```

### Карточки

Под нужной колонкой нажать `+ Add item`, вписать название, нажать Enter.
Отдельные задачи (Issues) создавать не обязательно: так получаются карточки-черновики.

Колонка `Done` - выполнено в первом цикле:

```
Структура проекта, README и .gitignore
Модели данных и схема базы
Регистрация и вход по JWT
API досок и задач с разграничением прав
Интерфейс доски с перетаскиванием карточек
Автотесты API и интерфейса
Настройка CI, линтеров и pre-commit
```

Колонка `Backlog` - развитие проекта:

```
Комментарии к задачам
История перемещений задач (журнал действий)
Обновление доски в реальном времени (WebSocket)
Фильтр по исполнителю и приоритету
Экспорт доски в CSV
Поддержка нескольких досок
```

## 5. Порядок работы с задачей

1. Тимлид создаёт Issue и переносит карточку в `Ready`.
2. Разработчик берёт задачу, переносит в `In Progress` и создаёт ветку
   по шаблону `feature/ISSUE-ID-short-name`, например `feature/12-task-comments`.
3. Коммиты с осмысленными сообщениями: `feat: add comment model`.
4. Pull Request по шаблону со ссылкой `Closes #12`, карточка уходит в `Code Review`.
5. CI запускается автоматически: стиль, форматирование, тесты, сборка.
6. Ревьюер оставляет замечания, разработчик вносит правки и получает approve.
7. После слияния карточка переходит в `QA`, тестировщик проверяет по чек-листу.
8. Проверено - карточка в `Done`, Issue закрывается автоматически.

## 6. Выпуск версии

```bash
git tag -a v0.1.0 -m "MVP: доска, роли, перетаскивание, тесты и CI"
git push origin v0.1.0
```

Затем Releases -> Draft a new release -> выбрать тег `v0.1.0`,
в описание скопировать соответствующий раздел из `CHANGELOG.md`.
